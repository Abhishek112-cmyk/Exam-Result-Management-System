01 · Problem Definition (PS No. 48)

Problem Statement & Core Rules

Educational institutions need an accurate, fast way to record subject marks, validate boundaries, compute percentages & Pass/Fail status, search by ID, rank students, and persist records across sessions.

Rule 1 Sequential IDs
First generated Result ID is ER101, incrementing automatically (ER102, ER103, …) and resuming from the highest saved ID at startup.
Rule 2 Marks & Pass Rule
3 Subjects, each scored strictly in [0, 100]. Total out of 300. Student Passes if Percentage ≥ 40.00%, else Fails.
Rule 3 Custom DSA Logic
Records stored as objects in ArrayList<StudentResult>. Searching & Sorting are written from scratch (zero built-in sort/search calls).
📋 Menu Operations
1 Add Result  |  2 Display All  |  3 Search by ID  |  4 Sort by Percentage (High → Low)  |  5 Save & Exit
💾 Persistent File Storage + Dual UI
Loads results.txt automatically on startup and saves on exit. Packaged in one .java file supporting both Console Mode & Java Swing Desktop GUI.

💡 Quick Viva Reference (Click a Question)
1. Why use ArrayList instead of a standard Java array?
Standard arrays have fixed capacity. ArrayList resizes dynamically as new students are added while still giving O(1) index access (get/set) needed for in-place Bubble Sort swaps.
2. Why Linear Search instead of Binary Search for IDs?
Binary Search requires records to remain sorted by ID. Once the user runs Option 4 (Sort by Percentage), records are ordered by marks rather than ID—Linear Search works reliably in any order.
3. How does Bubble Sort achieve O(N) in the best case?
A boolean swapped flag tracks whether any swap occurred during a pass. If a pass finishes with swapped == false, the list is already sorted and the loop breaks immediately in O(N).
4. Why divide by 300.0 instead of 300 in percentage calculation?
Integer division truncates decimals (103 * 100 / 300 = 34). Using floating-point 100.0 / 300.0 preserves exact precision (34.33%).
